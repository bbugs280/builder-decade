# 2026-10-17 — Post #47: AI cost is cost of goods, not leverage

**Decision context:** the builderdecade Stage-3 gate and the traffic-constraint ledger
both said **content volume is SPENT** (46 posts, ~1 EN click/30d, five page-1 queries
at positions 3.8–5.8 with 1 click between them). Referral links are the live
constraint. Vincent nonetheless chose to write **one more post** rather than work
the referral layer, and chose **full post** over a fold-in.

That choice is recorded here honestly: this post is not expected to move traffic.
It was built to be **worth linking to** — a terminal-action asset with a citable
arithmetic, positioned to pick up referral/internal links rather than clicks.

## What shipped

New post: **`ai-cost-of-goods`** (EN + ZH).

```
EN   content/posts/ai-cost-of-goods.md
ZH   content-zh/posts/ai-cost-of-goods.md
IMG  assets/cover-ai-cost-of-goods.png            (1344×768)
```

**Thesis:** AI spend is not leverage; it is cost of goods. The only number that
means anything is its **share of revenue**. A one-person company spending >$1M on
AI to make ~$3M is a **~33% COGS business** — respectable, behaves like
manufacturing, and is *not* the near-free leverage the genre claims.

**Axis check (collision guard):** distinct from `ai-api-cost-creep`, which is about
per-token cost creep within a single project. This post owns **AI spend as a
percentage of revenue / COGS at company scale**.

## Terminal action — new `mode="cogs"` on the shared `solo-calc` shortcode

`layouts/shortcodes/solo-calc.html` gained a 5th mode:

```
inputs   AI spend/month · revenue/month · other COGS
output   AI as % of revenue · total COGS % · gross margin $/mo · band verdict
```

Bands: rounding-error · lean · normal · heavy. Zero-revenue guard returns a prompt
rather than dividing by zero. The verdict text also states the $1M/$3M benchmark
ratio so the reader can see where they sit against it.

i18n: 12 new keys added to **both** `i18n/en.yaml` and `i18n/zh.yaml`.

## Bugs found and fixed during the pass

### 1. ⚠️ Calculator band boundary — the benchmark case was mislabelled

At the story's own reference ratio (1,000,000 / 3,000,000 = **33.333%**), the
verdict read **"Heavy"** — the post's central example was being flagged as a
warning. Cause: `aiPct <= BENCH` compares a float against `33.3`, and
`33.333… > 33.3`, so the reference case fell straight into the next band.

Fixed with a small tolerance on the boundary comparison. **Verified in the
built, minified output**, driving the real inputs in a browser:

```
1000000 / 3000000 / 1  -> "In the normal band"          ← was "Heavy" before fix
     100 / 10000 / 0    -> "rounding error"            (1.0%)
    1500 / 10000 / 0    -> "Lean"                       (15.0%)
    4000 / 10000 / 0    -> "Heavy"                      (40.0%)
     500 /      0 / 0    -> "Enter your monthly revenue" (guard holds, no NaN)
```

This defect was invisible to the build and to all four gates. It was only caught
because the arithmetic was actually exercised — the same lesson as
`docs/changes/2026-09-25.md`.

### 2. Cover generation failed house style on the first attempt

First cover rendered a **meter/gauge face with numerals 0–50 on the dial**. The
repo's house style forbids text and numerals in covers, and instruments reliably
pull markings out of the model. Re-wording the negative prompt does not fix this —
**changing the object does.** Regenerated with blank cardboard crates as the
subject. Verified 1344×768, no text, no numerals.

### 3. ZH defects caught after the first build

- ZH `cover.alt` still carried the **old** English meter description → rewritten to
  describe the actual regenerated image.
- One Simplified character 「门」 → 「門」 in the ZH body. Note: the traditional
  checker **passed this** — a single Simplified char falls below its ≥10-file
  threshold. Single-character escapes are a known blind spot of that gate.

## Post-gate fixes (build-tester verdict was ⚠️, all four addressed)

The build-tester quality gate returned **⚠️ ship with warnings** and found four
defects I had missed — including one where my own changelog asserted a false
justification. All four are fixed below.

### F1. 🔴 The ZH calculator was written in Cantonese — and my justification was false

I wrote all 12 new `i18n/zh.yaml` strings in **spoken Cantonese 口語** and then
justified it in this changelog as *"matching the rest of the ZH site."* **That claim
did not survive checking:**

```
existing i18n/zh.yaml (213 lines)     0 Cantonese particles
46 of 47 ZH post bodies               0 Cantonese particles
the one exception                     ai-api-cost-creep.md — 4, all mine
new i18n strings                      係×13 嘅×9 呢×5 唔×4 嘢×3 喺×2 幾多×2 佢×2
```

The ZH site is written Mandarin. My calculator was the only thing on it speaking
Cantonese. **Rewritten:** all 12 keys + the inbound line in `ai-api-cost-creep.md`
now in written Traditional Mandarin (「佔營業額多少」, 「就是」, 「這裡所有內容」,
「不是商業模式」). Verified: **0 Cantonese particles across all 47 rendered ZH pages.**

Lesson: I asserted a house-style justification without checking the corpus first.
The corpus is checkable and I should have checked it.

### F2. 🟡 Band ignored `othercogs` — verdict and detail judged different numbers

`$1M/$3M` revenue with `$900K` other COGS returned *"In the normal band — this is
manufacturing economics"* while the detail line beneath it reported **63.3% total
COGS**. A 63%-COGS business was being called normal.

Fixed: the band is now driven by **total COGS**, not AI spend alone. Same case now
returns *"Above half your revenue."* Also added a **negative-gross guard** — if other
costs exceed revenue the verdict says so plainly instead of banding a minus sign.

### F3. 🟢 Display/band rounding desync

`15.01%` displayed as `"15.0%"` while banding LEAN→NORMAL, so the reader saw a number
that contradicted its own label. Detail percentages moved `toFixed(1)` → `toFixed(2)`;
the visible number now sits on the same side as the verdict at every boundary.

### F4. 🟢 One-way linking + tag mismatch

New post had **zero outbound sibling links**. Added two (`/posts/ai-api-cost-creep/`,
`/posts/metered-build/`) in both languages, in the section where the per-project
discipline is the natural next step. ZH tag set was missing an `ai leverage`
counterpart → added 「ai 槓桿」 (6 EN / 6 ZH).

### F5. 🔴 BONUS — Simplified Chinese was rendering on ALL 47 ZH pages

Build-tester noted the ZH reading time showed 「1 分钟」 and flagged that `钟` is
**Simplified** (`分鐘` in Traditional). Investigating the source found it was worse
than a word-count quirk:

**PaperMod's vendored `themes/PaperMod/i18n/zh.yaml` ships in Simplified Chinese** —
`上一页`, `下一页`, `目录`, `语言`, `1 分钟`, `复制`, `主页`, `编辑`. Every one of the 47
ZH pages was rendering Simplified chrome, and `check_zh_traditional.py` could **never**
catch it because it scans `content-zh/posts/*.md` only — the strings never appear in
a content file.

Fixed at source, but **not via i18n** — see the durability note below. Chrome now renders
「1 分鐘」, 「語言:」, 「主頁」, 「上一頁」 in Traditional.

**New permanent gate added: `tests/check_zh_traditional_theme.py`** — scans built
HTML for known theme-sourced Simplified leaks. Critically, it was **proven to fail**
before being trusted: with the theme reverted it reported 916 occurrences across 4
characters and exit code 1; after the fix it returns exit 0.

### ⚠️ Durability — why a site i18n override would NOT have worked

`themes/PaperMod` is a **git submodule** pinned to upstream. Editing
`themes/PaperMod/i18n/zh.yaml` fixes the build on this machine and silently reverts
on any fresh clone or CI build.

The documented fix — a site-level `i18n/zh.yaml` override — **does not work in Hugo
0.165.** Verified empirically rather than assumed:

```
theme reverted to upstream + site i18n override present
  → hugo --minify
  → built output still renders "1 分钟"  (Simplified)
  → theme i18n wins over site i18n for these keys
```

So the fix lives in **site-level LAYOUT overrides**, where site-over-theme
precedence does hold. Five partials + one template are now copied into the repo and
patched with a `eq site.Language.Lang "zh"` branch, falling through to the original
`i18n` call for EN:

```
layouts/_partials/post_meta.html          read_time       → 分鐘
layouts/_partials/translation_list.html   translations    → 語言
layouts/_partials/footer.html             code_copy/copied → 複製 / 已複製！
layouts/_partials/breadcrumbs.html        home            → 主頁
layouts/_partials/post_nav_links.html     prev/next_page  → 上一頁 / 下一頁
layouts/list.html                         pagination      → 上一頁 / 下一頁
```

Verified with the submodule **pristine** (`git status` in the theme is clean) and a
from-scratch build: all five gates pass, EN chrome unchanged (`« Prev`,
`Translations:`, `copy`), ZH fully Traditional.

⚠️ **Maintenance cost accepted:** these six files are forks of theme internals. If
PaperMod changes `post_meta.html` upstream, the override must be re-synced or the
change is silently masked. Each file carries a header comment saying so.

During the fix the footer patch was first applied wrongly — a sloppy replace broke
the `setTimeout` callback into a malformed function. Caught by reading the diff,
reverted from the theme, and reapplied surgically; `setTimeout` presence is now
checked in the built output.
