### ⚠️ UNIT BUG in the calculator — found by the adversarial gate, fixed before commit
The first version computed the hire ratio as `revPerHour * hours / needed`, which **divides a weekly revenue figure by a monthly cost** — a mixed-unit comparison that made **every verdict ~4.33× too pessimistic**. On the shipped default it read **ratio 0.96 → "the hours don't pay for the hire"** when the correct value was **4.16 → "clears the cost comfortably"**. The detail line compounded it by printing `money(revPerHour * hours)` (a *weekly* figure) with a `/mo` label.

**Fixed:** `ratio = revenue / needed` (monthly vs monthly — like with like), and the handover figure recomputed as `revenue * (hours / 168)` for a true monthly value.
**Post-fix verification** (`/tmp/verify_fixes.py`): corrected formula present in the built HTML, stale formula absent, factor between old and new measured at **4.330**, default band now **YES**.

This is the second defect of the session that a *build pass could not catch* — the first being the default-value problem below. Both required independently recomputing the arithmetic.

### ⚠️ Default-value bug (fixed before commit)
The hire calculator's original defaults (revenue 12,000 / 15 hrs) produced a **negative first impression** — the reader's first sight of the widget was "the hours don't pay for the hire." ### ⚠️ Privacy note overclaimed — corrected
The widget note said "the page never sees your figures." The site carries site-wide **Google Tag Manager and AdSense** (pre-existing, unrelated to this change), so that sentence could be over-read as covering the whole page. Rewritten (EN + ZH) to scope the claim precisely: the *widget* makes no network call, stores nothing, and has no analytics — while noting the site carries standard analytics elsewhere.
