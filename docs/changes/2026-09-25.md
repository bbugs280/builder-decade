### ⚠️ UNIT BUG in the calculator — found by the adversarial gate, fixed before commit
The first version computed the hire ratio as `revPerHour * hours / needed`, which **divides a weekly revenue figure by a monthly cost** — a mixed-unit comparison that made **every verdict ~4.33× too pessimistic**. On the shipped default it read **ratio 0.96 → "the hours don't pay for the hire"** when the correct value was **4.16 → "clears the cost comfortably"**. The detail line compounded it by printing `money(revPerHour * hours)` (a *weekly* figure) with a `/mo` label.

**Fixed:** `ratio = revenue / needed` (monthly vs monthly — like with like), and the handover figure recomputed as `revenue * (hours / 168)` for a true monthly value.
**Post-fix verification** (`/tmp/verify_fixes.py`): corrected formula present in the built HTML, stale formula absent, factor between old and new measured at **4.330**, default band now **YES**.

# Follow-up — Calculator was functional but not discoverable (Vincent, same day)

**Trigger:** Vincent, after the push: *"seems the calculator is not obvious as a tool.."*

## What was actually wrong

The calculator **worked** — but on the live page it rendered as **plain prose with invisible numbers**. Root cause: the shortcode shipped **no CSS of its own**, and PaperMod resets every `input` to `border: 0` / `background: transparent`. So there was no box, no affordance, and no visual signal that the numbers were editable.

```
computed style BEFORE (live):
  input border      0px none
  input background  rgba(0,0,0,0)   <- identical to page background
```

The prior verification pass had checked the widget by **grep + arithmetic recomputation only**. Both passed, because the maths and the markup were correct. Neither can see that a control is invisible. This is the gap the previous entry's own "Open" section flagged.

## Fixes

1. **Added the missing CSS** (`assets/css/extended/custom.css`, ~145 lines). Inputs get a real bordered box, tabular-nums, right-aligned, amber focus ring, hover affordance; container gets a 2px amber border so it reads as a widget rather than a card; spinner clutter removed.
2. **Added an `Interactive —` badge** above the fields so tappability is signalled before the reader scrolls past.
3. **Added unit markers** (`$`, `%`, `hrs`, `wks`) so a bare `60000` reads as currency rather than an arbitrary number — 4 new i18n keys per language.
4. **Made the result block read as output**, not body copy (4px amber left rule, bold verdict).
5. **Dark mode**: all colours via brand palette vars; verified the widget follows the theme.

## Bugs found while verifying (both real, both fixed)

- **ZH detail line was half-English.** The verdict was translated but the detail string was **hardcoded English inside the `<script>`**. Converted to i18n with `{placeholder}` substitution — 2 new keys per language. ZH now reads fully Chinese.
- **Dark-mode border did not follow the theme.** Root cause: `assets/css/extended/custom.css` declared the PaperMod var mapping (`--border: var(--line)` etc.) **only under plain `:root`**. That block also matches the dark root and wins the cascade, pinning the value to the LIGHT palette and preventing re-resolution on theme switch. Fixed by giving the mapping a `:root[data-theme="dark"]` counterpart.

Drove a headless browser against the built site and clicked PaperMod's **own** theme toggle — the real user path:

**Behavioural check:** dispatching real `input` events on the revenue field flipped the verdict across all three bands —
`3000 -> "don't pay for the hire yet"`, `26000 -> "clear the cost comfortably"`, `200000 -> "clear the cost comfortably"`.

**Method note worth keeping:** several apparent failures during this pass were **artifacts of my own test harness**. Calling `documentElement.setAttribute('data-theme', ...)` directly — bypassing PaperMod's JS — left the page in a state where style recalculation did not propagate, producing a reproducible "border stuck in light mode" reading that did not exist for a real user. Every such reading was invalidated once tested through the real theme toggle. **Test theme behaviour through the app's own control, never by poking the DOM attribute.**

Also: the auxiliary vision model produced **fabricated** descriptions of this page twice (invented a construction photo, a "2017" date, and a table of home-improvement costs). Visual claims were discarded in favour of DOM geometry. Do not use that model as evidence for this kind of check.

## ⚠️ Correction to my own reasoning (caught by the gate)

I claimed the white fill was *"what makes a box read as an editable field."* **That was false.** I compared the field to the **page** and never to its actual container:

```
input  rgb(255,255,255)   vs   card .solo-calc rgb(255,255,255)
delta [0,0,0]  →  contrast 1.0000
```

The input sits inside a **white card**, so a white fill is invisible. The border was doing 100% of the work. Fixed by inverting the logic — the field is now *darker* than the card (`#F4F1EC` vs `#FFFFFF`, delta `-11,-14,-19`), which is what a recessed input actually looks like.

Dark mode had the same defect (1.14:1) and the identical fix (`#1A1917` vs card `#23211D`).

Also fixed: the focus ring was `rgba(180,85,29,0.22)` → **1.348:1**, below the WCAG non-text minimum of 3:1. Now solid amber at **6.51:1**.

## Method note — the `setAttribute` trap, again

Reading theme values by calling `documentElement.setAttribute('data-theme', ...)` directly produces **corrupt readings** (it reported light values while in dark mode). This bit me twice, in two separate sessions. **Always drive theme switching through PaperMod's own `#theme-toggle` button and let the 0.15s transition settle.** DOM-attribute poking is not a valid test method here.
