## Finding 2 — 🔴 two ZH posts were written in SIMPLIFIED Chinese (unrelated, found while editing)

While adding the ZH links I noticed `how-to-get-first-users-solo`'s Sources block was Simplified.
Scoped it properly across all 38 ZH posts:

```
reuse-vs-rebuild.md            344 divergent chars of 2009 CJK   ← SIMPLIFIED
how-to-get-first-users-solo.md 326 divergent chars of 1988 CJK   ← SIMPLIFIED
(next worst: 2 chars — false positives)
```

**This breaks a stated site guardrail**: `i18n/zh.yaml` is Traditional and 35 of the 37 other ZH
posts are Traditional. It matters more than usual here because **ZH is this site's only converting
lane** (`ship-one-tiny-thing` at pos 1.0 is the site's sole converting page).

**Root cause — a test gap, not a one-off:** `tests/test_language_isolation.sh` guards EN-vs-ZH bleed
but has **no Traditional-vs-Simplified check at all**. A Simplified body passes every existing test.

**Fixed:**
1. Both files rewritten in **natural Traditional Chinese** (Taiwan/HK usage), not a glyph map —
   `使用者` not `用户`, `程式碼`, `函式庫`, `依賴`, `終止`, `走鐘`, `回饋`, `專案`, `建置`.
   Frontmatter values (title/tags/alt) converted; link paths, structure, bold/italic markers and
   `## Sources` headings preserved byte-identically.
2. **New guard added: `tests/check_zh_traditional.py`** — flags any ZH post with ≥10 characters from
   a curated Simplified-divergence set. Catches this class permanently.

⚠️ **The guard's first draft was itself buggy** and is worth recording: the divergence set included
`向`, `量`, `台`, `准`, `制`, which are **identical or legitimately interchangeable** in Traditional
(`內向`/`流量`/`控制` unchanged; `准許` is valid Traditional; `台`/`臺` are both correct). It therefore
flagged 4 *correct* Traditional posts as failures — a false-positive test that would have blocked all
future ZH work. Verified against OpenCC `s2t` and the set was narrowed. **A guard that cries wolf is
worse than no guard** — same lesson as the broken-probe pitfalls in `decade-content-pipeline`.

## The build bug — worth recording, because it cost a session

The post was **created correctly and never built**. Symptoms:

```
hugo list all        post listed ✓, draft:false, permalink correct
public/posts/        39 dirs for 40 md files — mine simply absent
hugo build           exit 0, no error, no warning, no mention of the file
```

Every hypothesis I chased first was **wrong**: frontmatter BOM, `translationKey` collision, cover
image path, cover file size (1.67 MB — but other covers are the same and build fine), filename. The
giveaway, once I stopped guessing and did a bare-minimum reproduction, was that **a trivial 9-line
probe file with minimal frontmatter was also skipped** — so it was never the content.

**Root cause: the post was dated in the future.**

```
post date       2026-09-21T20:00:00+08:00
wall clock      2026-09-21T19:25 HKT
```

Hugo silently omits future-dated content unless `--buildFuture` is passed. No warning, no error, and
`hugo list all` still lists it (it reports planned content). `hugo --buildFuture` rendered it
immediately — which both proved the cause and confirmed the content was fine all along.

**Fixed:** date set to `2026-09-21T18:00:00+08:00` (in the past) in both EN and ZH.

⚠️ **Lesson for the pipeline skill:** a new post dated "today" with a time later than the build time
will silently vanish. Two defences: date new posts to a time already past, or confirm presence in
`public/` before declaring a post shipped. The "39 md vs 39 dirs" discrepancy was the only symptom —
worth checking as a matter of course.

Also corrected while in there: the cover `alt` text said "a locked door standing open" but the
generated image is a **strongbox** — `alt` now matches the actual image in both languages.

## 🔴 Defect caught by build-tester — double-encoded shortcode JSON

The mandatory quality gate found a real defect I would otherwise have shipped.

```
symptom   interactive verdict box renders with literal quote marks around the text
cause     layouts/shortcodes/agent-reach.html applied `| jsonify` to an i18n value
          that was ALREADY a quoted string inside <script type="application/json">
emitted   "agent_reach_v0": "\"Nothing ticked yet. ...\""
effect    JSON.parse yields a value with literal quote chars; the shortcode JS writes
          it into the verdict element via textContent → reader sees the quotes
scope     5/5 verdict bands, EN and ZH
```

⚠️ **Why no test caught it:** it only manifests **after interaction** — the server-rendered
initial state (and therefore all static HTML checks) is clean. This is precisely the blind spot
a static test suite has for JS-driven shortcodes.

**Fixed:** dropped `| jsonify` from the 5 payload lines; the surrounding quotes now stand.
Verified clean in both languages:

```
EN  "agent_reach_v0": "Nothing ticked yet. Tick every statement that is true of your setup."
ZH  "agent_reach_v0": "還沒勾選任何項目。把所有符合你設定狀況的敘述都勾起來。"
```

**New guard: `tests/check_shortcode_json.py`** — parses every `<script type="application/json">`
payload in the built output and fails if any value is double-encoded (parsed value starts/ends with a
literal quote) or fails to parse. Covers the whole class, not just this shortcode.

⚠️ **The guard was proven to fail before being trusted** — double-encoding was re-injected into the
built HTML and the guard correctly reported it (exit 1) before the file was restored. A guard that has
never been seen failing is not a guard. (Same discipline as the `check_zh_traditional.py` false-positive
episode above.)

⚠️ **Note for future shortcodes:** the sibling `mcp-audit.html` avoids this entirely by inlining i18n
directly into JS string literals rather than via a JSON payload. That is the safer pattern for new
terminal actions.
